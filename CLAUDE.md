# CLAUDE.md

Guidance for working in the `bico` repository.

## Git / commit conventions

- **Never commit unless explicitly asked.** Make and stage changes freely, then stop and let the user request the commit.
- **Never add `Co-Authored-By:` trailers** (or any co-author/attribution) to commit messages or PR bodies. Write plain commit messages.

## Project overview

`bico` (Binary Converter) converts ETH eddy covariance raw data from a compressed binary format to uncompressed ASCII CSV files for use in EddyPro. It is an installed package (`bico/`) exposing a `bico` console command, with both a PyQt5 GUI and a CLI.

## Environment & tooling

- Dependency management uses [`uv`](https://docs.astral.sh/uv/) (migrated from poetry). Source of truth: `pyproject.toml` (PEP 621), locked in `uv.lock`.
- Requires Python 3.12.
- Set up the environment: `uv sync`
- Run the TUI: `uv run bico -t` (also the default when run with no args: `uv run bico`)
- Run headless: `uv run bico -f <folder> -d <days> -a` (also available as `uv run python -m bico ...`)
- Run the tests: `uv run pytest`

## Testing

- Tests live in `tests/` and use `pytest` (a dev dependency, in the `dev` group of `pyproject.toml`).
- `tests/conftest.py` exposes the installed package location; tests import the conversion modules directly
  (`from bico.ops import bin`). Importing the `bico` package is light and does not pull in the Textual TUI.
- The main test is a golden-file test: it converts a small truncated real binary
  (`tests/data/*.X00`) and asserts the output matches a committed expected CSV (`tests/data/*.golden.csv`).
  The conversion output must stay byte-for-byte stable, so this guards against regressions in converted values.

## Architecture notes

- `bico/bico.py` — entry point (`main_cli`); `BicoEngine` (conversion), `BicoFolder` (headless CLI). `bico/__main__.py` enables `python -m bico`.
- `bico/tui/` — Textual TUI: `app.py` (`BicoApp`, settings form + live Rich console; drives `BicoEngine` from a worker thread; `DirectoryPickerScreen` folder browser, `HelpScreen` help overlay), `app.tcss` (modern dark theme), `log_handler.py` (routes the engine logger into the on-screen `RichLog`; `format_log_line` turns each already-formatted `"ts | LEVEL | msg"` line into a multi-span coloured `rich.text.Text` — level colours, banners, file banners, numbers, bracketed units, keywords — while preserving the plain text exactly; the saved log file stays plain). A live status area (`#run-status`, `height: auto`) shows one line per in-progress file (`_file_status` maps task index -> progress; `_render_file_status` redraws all lines), each with a per-file progress bar/%, filename and step, so parallel workers each get their own line; a file's line is dropped on its `Done` event. The console is a `SelectableRichLog` (a `RichLog` subclass): plain `RichLog` (Textual 8.2) doesn't implement the selection hooks, so its `render_line` stamps each line with `apply_offsets` (so a mouse drag forms a selection), paints the selection highlight, and `get_selection` returns the selected text. The highlight uses only the `screen--selection` *background* (`_selection_style`), not the component style as a base — the theme's selection foreground is `transparent` ("keep existing"), which as a base style turns uncoloured text invisible. Copy: the App's default `ctrl+c` only shows a "press q to quit" hint for non-Input widgets, so `BicoApp` rebinds `ctrl+c` to `action_copy_selection` (`screen.get_selected_text` → `copy_to_clipboard`). The `#actions` bar is `dock: bottom` in the settings pane so it never overlaps the scrollable fields (which previously hid the lower fields, e.g. the output folder, on short terminals). Imported lazily so headless/test paths never need Textual. Note: the busy flag is `self._busy`, NOT `_running` (which collides with Textual `App._running`). **Validate** (`action_validate`) gates **Run**: `_validated` is cleared on any `Input/Select/Switch.Changed` and set true only when validation has no errors; `_refresh_run_enabled` enforces it. **Test run** (`_test_run` worker) dry-converts the first `TEST_RUN_ROWS` rows of the first file via `bin.ConvertData` and writes nothing. **Stop** (`#btn-stop`, enabled only during a run): `action_stop_conversion` sets a `threading.Event` (`_stop_event`); the engine is given `should_stop=self._stop_event.is_set` and polls it between files (`BicoEngine._stop_requested`), so the in-progress file finishes, queued/not-yet-started pool files are cancelled, and the run winds down normally (partial stats still exported).
- `bico/ops/` — `bin.py` (binary->ASCII core). Two decode paths share one precomputed per-datablock plan: a **vectorized fast path** (`_build_fast_plan` flattens the plan to fixed byte offsets; `_try_fast_convert` decodes the whole file at once with numpy via `np.frombuffer` over the mmap, ~25x faster) and a **sequential fallback** (`convert_to_ascii`, mmap + `int.from_bytes`, one field at a time). `run()` tries the fast path and falls back when the format is not fast-eligible (unknown `conversion_type`, the `status_code_lgr` quirk) or when any `DATA_SIZE` field shows a short/missing data block (which breaks the fixed-stride assumption — e.g. the IRGA72 16-vs-26-byte case). Both paths produce byte-for-byte identical CSV (guarded by the golden test, which exercises both). `get_dataframe(header)` assembles the frame from either source. `parallel.py` (per-file worker), `file.py` (search/IO; `search_glob_from_datetime_format` + `datetime_parsing_string` derive the file glob and strptime pattern from the filename datetime format — there is no separate file-extension setting), `stats.py`, `vis.py`, `setup.py`, `cli.py`, `logger.py` (shared log format + per-run logger reset), `log_report.py` (builds a self-contained HTML viewer for a run's log — see below).
- Conversion runs one file per worker process via `ProcessPoolExecutor` (`BicoEngine.loop` -> `ops.parallel.process_file`), with a sequential fallback for a single file/worker. Worker count comes from the optional `num_processes` setting (default `1`), else `cpu_count - 1`. Each file's captured log is replayed (and its stats collected) as soon as that file finishes — `_consume_result`, called from a `wait(..., FIRST_COMPLETED)` drain loop in `_run_pool` (parallel) or inline (sequential) — so the console updates live instead of dumping at the end (parallel order is completion order). Two callbacks: `progress_callback(done, total)` for the files-done bar, and `file_progress_callback(idx, total, filename, step, fraction)` for the live per-file status. Per-file progress flows from `ops.parallel._make_reporter`: sequential uses an in-process callable (`task['progress_cb']`), parallel uses a picklable `multiprocessing.Manager().Queue()` (`task['progress_queue']`, created only when a UI requested it) drained by `_drain_progress_queue`. `bin.ConvertData(progress_cb=...)` reports the converting fraction (bytes read / file size) every ~8192 rows on the sequential path (the vectorized fast path decodes in one shot, so it just reports `1.0` once). Stats and plots are computed from the in-memory converted frame — there is no CSV re-read. `ops.vis` forces matplotlib's `Agg` backend so plotting works in workers.
- **Per-run HTML log viewer.** A run logs to a plain `{run_id}.log` as before; at the very end (`BicoEngine._write_log_html_viewer`, after `_log_bicofinish`) it renders a self-contained `{run_id}.log.html` next to it via `ops.log_report.write_log_html`. The markup lives in `bico/ops/log_viewer_template.html` (a single-file, offline, searchable/colour-coded viewer that mirrors the TUI's `log_handler` styling, and which also works standalone as a drag-and-drop viewer when opened directly). Building a per-run page just substitutes the log as a JS string at the `/*BICO_EMBED*/` marker (`<` escaped to `<` so the embedded text can't close the `<script>`); all parsing/rendering happens in the browser, so it stays fast even for large logs and never blocks the run. Failures are non-fatal — the plain `.log` is the source of truth.
- `bico/settings/data_blocks/*.dblock` — data-driven format specs (one per instrument/logging variant), each parsed as Python dict literals. Adding instrument support means adding a `.dblock` file, not changing code. Companion `.md` files document each block.
- The settings file is `bico.settings` (lowercase). `file.SETTINGS_FILENAME` is the canonical name; `file.find_settings_file` locates it in a folder case-insensitively so legacy `BICO.settings` folders still load (used by the headless CLI `BicoFolder`). A run never modifies the source `bico.settings`; it writes a `bico.settings` snapshot into the run's output folder. The TUI's "Save settings" persists only user keys (`file.save_settings_to_file`); derived/runtime keys are excluded. The TUI's run-only options (`days`, `avoidduplicates`) are not persisted. The TUI's **Export…** button (`e` / `action_export_settings` / `#btn-export`) writes the current form values as a `bico.settings` into a folder chosen via `DirectoryPickerScreen` (`file.export_settings_to_folder`), for seeding a headless run folder; it never touches the source `bico.settings`. Both Save and Export share `file._write_settings_from_template`, which renders a settings file by substituting values into a template (an existing `bico.settings`) while preserving comments and dropping `DERIVED_SETTING_KEYS`.
- The TUI loads `bico/settings/bico.settings` on startup (last saved = last used) and Save writes back to it. Drag-and-drop relies on terminals pasting a dropped file/folder as its path; the shared parser is `_parse_dropped_path` (handles quotes and `file://` URIs), with `_dropped_settings_file` and `_dropped_folder` on top. Dropping a `bico.settings` file anywhere (when no Input is focused) loads it via `BicoApp.on_paste` → `_load_settings_from_path`. The source/output folder fields are `PathDropInput` (an `Input` subclass): its `_on_paste` fills the field with the dropped folder (a dropped file → its parent). Note Textual dispatches `_on_paste` for every class in the MRO, so `PathDropInput._on_paste` must call `event.prevent_default()` to stop `Input._on_paste` from also inserting the raw text. A terminal routes a dropped path to the *focused* widget (it does not report the cursor position during an external OS drag, so hover-based routing is not viable), so the field must be focused before the drop; a drop with no Input focused bubbles to `BicoApp.on_paste`, which only handles a dropped `bico.settings` file. Each folder field also has a `…` browse button and a `✕` clear button (`clear-<key>`, handled by `_on_clear_field`).
- **Detect dates** (`action_detect_dates` / `d` / the `#btn-detect` button under Raw data) scans the source folder off-thread (`_detect_dates` worker), parses each filename with `bfile.datetime_parsing_string(fmt)`, and fills Start/End date with the earliest/latest file via `_apply_detected_range` (which also resets `days` to 0 so the explicit range is used). Requires only the source folder and filename datetime format.
- Internal imports are package-qualified (`from bico.ops import ...`); the package is installed editable via `uv sync` and `[project.scripts] bico` points to `bico.bico:main_cli`.
- Version is set in `bico/settings/_version.py` and `pyproject.toml` (kept in sync by a test).
